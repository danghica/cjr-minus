# Unanimity / Pareto efficiency

## Theorem

If every voter strictly prefers valid candidate A to candidate B, no completed
execution of the checked CJR− election returns B. In Lean,
`election_pareto_all_profiles` in `Pareto.lean` states:

```lean
theorem election_pareto_all_profiles (ha : a < n)
    (hu : ∀ row ∈ bs, Prefers row a b) (s t : State) :
    ¬ ElectionResult n bs s (.lit (.int b)) t
```

The candidate IDs `a` and `b` are natural numbers. `ElectionResult` refers to
successful construction and actual `Cjr.Evaluates` small-step execution, as in
the anonymity theorem. It is not defined through a voting oracle. There are no
voter-count, ballot-length, or fuel bounds.

`election_pareto` takes an explicit nonempty-electorate assumption through
`UnanimouslyPrefers`. `election_empty_no_winner` handles the empty case, making
the universal-preference formulation above valid for zero voters as well.
`election_winner_not_dominated` states that any returned value differs from B;
`election_run_pareto` gives the corresponding result for the executable `run`.

## Partial rankings

`Prefers row a b` means that A occurs and its index is strictly less than B's
index. An omitted candidate has index `row.length`. Thus `[A,B]` and `[A]` both
prefer A to B; omitting both gives no strict preference. The checked builder
still rejects repeated or unknown IDs within a ballot. Repeated voters' ballots
are allowed. Unranked candidates are never strictly preferred to each other.

## Implementation change

The checked `election` entry point now wraps the existing counting program in a
**CJR return-value guard**. During checked input preparation it computes the IDs
not unanimously dominated by any valid candidate. The generated CJR program runs
the election, including cleanup, then compares its result against those IDs:

- An eligible ID is returned unchanged.
- Any other result becomes `-1`, the existing no-winner/error sentinel.
- An empty electorate has no eligible winner.

The counting core and its tie-breaking are unchanged. The guard executes in CJR
and appears in the emitted Cangjie sample. It does not rely on a correctness
assumption about the core.

This is a safety check, not a proof that the unguarded counting core can never
return a dominated candidate. In particular, the theorem does not prove that
the fallback is unreachable on valid input. The regression suite compares the
guarded program with the independent instant-runoff oracle, and all cases agree.

## Machine-checked proof

1. `unanimousAbove_iff` connects the executable preference test to its definition.
2. `paretoCandidates_excludes` proves that unanimous preference for valid A over B
   excludes B from the eligible list.
3. `unanimouslyPrefers_perm` transfers this premise through canonical voter order.
4. `ReturnsOnly` in `ReturnSafety.lean` certifies return-value properties of CJR
   expressions. Its `step`, `steps`, and `sound` theorems prove preservation under
   actual small-step execution and establish the property at completion. The
   initializers and conditions may be arbitrary effectful CJR programs.
5. `paretoGuard_safe` certifies that the guard returns only eligible IDs or `-1`;
   `election_return_safe` certifies the actual program built by `election`.
6. B cannot be eligible, and natural candidate ID B cannot equal `-1`. Therefore
   no completed execution can return B.

`paretoGuard_accepts` additionally proves a positive property: if the core
completes with an eligible candidate, the guard returns that same candidate and
leaves the core's final state unchanged.

## Scope and verification

This is partial correctness for the **updated checked entry point**. It does not
prove termination or require that a winner is returned. It also does not prove
the stronger claim that a unanimous first choice must be elected. It establishes
the precise requested exclusion property. Direct calls to `votingFn` or native
`rankedChoice` bypass the guard and remain outside the theorem. Correctness of
native code emission is a separate claim.

Run `sh check.sh` after building the parent library. It checks the theorem files
and axiom audits, 413 CJR elections against the independent oracle with Pareto
assertions, and 97 voter-swap cases. Guard tests inject five raw results: two
eligible IDs, a dominated ID, an unknown ID, and an invalid negative ID. Partial
ranking conventions and empty electorates are tested explicitly.

`python3 test_native.py` checks 262 native core elections and ballot preservation,
plus a generated guarded election and five generated injected-result checks.
`pareto_checks.cj` is regenerated by the Lean tests for that native verification.

The Pareto theorem's audit contains only Lean's standard `propext` and
`Quot.sound`. All proof terms are kernel-checked, with no admitted lemmas,
custom axioms, bounded enumeration, or `native_decide` used to prove the theorem.
